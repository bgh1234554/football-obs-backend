# 로컬 요청 제한 부하 테스트

2026년 10월 29일에 실제 Spring Boot HTTP 서버를 별도 JVM으로 실행해 측정했다. 부하 발생기와 외부 응답 모의 서버는 별도 Python 프로세스에서 실행했다. 실제 API-Football·BunnyCDN에는 접속하지 않았다.

환경변수 이름·값, 운영 기본값, 인증정보, 운영 URL은 이 보고서에 포함하지 않는다. 비교한 A·B는 로컬 실험용 공유 예산이며 운영 환경의 확정값으로 해석하면 안 된다. 실행 스크립트, 원시 결과와 JVM 로그는 Git에서 제외되는 로컬 작업 경로에 보관한다.

## 측정 범위

- 로컬 Windows, Java 23, 논리 CPU 16개 환경이다. Render의 CPU·메모리·네트워크를 재현한 것은 아니다.
- 실제 `/api/fixtures/last`와 `/api/fixtures/next`의 컨트롤러·서비스·JSON 가공·캐시·요청 제한을 사용했다. 응답은 팀당 6경기를 모의했다.
- 50명의 사용자가 각각 다른 IP를 사용하는 조건과, 같은 공인 IP 하나로 묶이는 조건을 구분했다.
- 반복 조회는 사용자당 매초 두 요청을 30초 동안 실행했다. 집중 조회는 사용자당 20요청을 연속 실행했다.
- 캐시 미적중 모의 응답에는 80ms 대기를 넣었다. 이는 실제 외부 API의 지연 분포를 재현한 값은 아니다.
- A와 B는 전체 외부 예산만 다르다. 서버 입구·개인별 외부 제한과 요청 데이터는 같다.
- 요청별 응답시간과 상태, 모의 외부 서버가 받은 실제 HTTP 횟수, JVM 프로세스 CPU 시간·RSS를 측정했다. 프런트의 429 자동 재시도와 이미지 다운로드는 실행하지 않았다.
- CPU·메모리는 실행기 프록시가 아닌 실제 JVM 프로세스를 측정했다. 모의 서버의 접속 대기열도 동시 접속 수를 수용하도록 설정했다.

## 캐시 반복 조회의 자원 사용

| 비교 | 처리량(req/s) | CPU(한 코어=100%) | 전체 논리 CPU 대비 | 최대 RSS(MiB) |
| --- | ---: | ---: | ---: | ---: |
| 공유 예산 A | 99.94 | 34.04% | 2.13% | 269.61 |
| 공유 예산 B | 99.95 | 32.80% | 2.05% | 268.29 |

CPU는 측정 구간의 JVM CPU 사용시간을 실제 경과시간으로 나눈 평균이다. 한 코어 기준 수치가 100%면 한 코어를 계속 사용한 양이고, 여러 코어를 동시에 쓰면 100%를 넘을 수 있다. RSS는 JVM의 힙뿐 아니라 네이티브 메모리 등을 포함한 프로세스 상주 메모리다. 짧은 집중 구간은 JIT·GC·스레드 준비의 영향을 크게 받으므로 지속 처리량의 근거로 삼지 않는다. 같은 PC의 다른 프로세스 영향도 배제한 전용 벤치마크는 아니다.

## 해석

### 캐시를 공유하는 50명

두 비교 모두 캐시 반복 조회 3,000건과 집중 조회 1,000건이 전부 성공했고 추가 외부 HTTP는 없었다. 같은 미캐시 데이터에 대한 동시 요청 100건도 외부 로딩은 두 URI에 대해 총 2회만 실행됐다. 이 로컬 실험에서는 캐시 적중과 동일 URI 병합이 외부 예산을 소모하지 않는 구조가 확인됐다.

### 서로 다른 데이터가 동시에 필요할 때

공유 예산을 늘린 B는 A보다 많은 외부 호출을 허용했고 나머지는 `upstream-global` 429로 막았다. 이는 서버 성능 부족으로 생긴 500이 아니라 설정한 외부 예산에 따른 거절이다. 캐시가 없는 서로 다른 요청을 모두 처리할 수 있는지는 사용자 수만으로 정할 수 없고 외부 호출 예산에도 달려 있다.

### 50명이 공인 IP 하나를 공유할 때

캐시된 데이터만 요청했는데도 서버 입구의 IP별 제한 때문에 다수의 429가 발생했다. 일반 가정별로 다른 IP를 쓰는 50명과, 같은 사무실·공유기·프록시 뒤의 50명은 다르게 동작한다. 따라서 현재 입구 설정을 모든 50명 사용 상황에 적합하다고 결론 내릴 수 없다. NAT 환경을 지원할 범위와 실제 서버 자원을 확인해 입구 예산 또는 사용자 식별 정책을 따로 정해야 한다.

## 소진율 로그와 회귀 검증

부하 실험의 전체 예산 소진 과정에서 `[UPSTREAM_BUDGET_USAGE]`의 단계 상승과 완전 소진 로그를 확인했다. 80·85·90·95%는 WARN, 100%는 ERROR이며 작은 버킷이 여러 단계를 한 번에 넘을 때는 가장 높은 도달 단계만 기록한다. 동일 단계 반복 방지와 60% 이하 회복 후 초기화는 가짜 시간 기반 단위 테스트로 별도 검증했다.

전체 회귀 테스트 120개가 통과했다. 테스트는 차감·캐시·동시성·로그의 기능 계약을 검증하며, 로컬 결과만으로 Render의 최대 동시 사용자 수나 외부 API 요금제 한도 준수를 보장하지 않는다. 실제 운영 기본값을 이번 측정만으로 자동 변경하지 않았다.

## 재실행과 자료 보관

부하 실험은 일반 회귀 테스트와 별도로 실행한다. 실제 서버 프로세스와 로컬 모의 외부 서버를 띄우므로, 일반 테스트 실행마다 자동으로 반복하지 않는다. 실험 종료 시 직접 시작한 JVM을 종료한다.

백엔드 저장소 루트에서 실행 JAR을 먼저 만든다.

```powershell
.\gradlew.bat bootJar
```

이 작업에 사용한 실험용 스크립트와 원시 결과는 Git에서 제외되는 로컬 작업 디렉터리에 보관했다. 실제 JDK 실행 파일을 지정해 실행기 프록시가 아닌 JVM 자체의 자원을 측정한다.

```powershell
python .codex-tmp/local-rate-limit-loadtest.py --java "<실제 JDK의 java.exe 경로>"
```

스크립트는 운영 환경변수 값을 출력하지 않고, 로컬 실험 전용 설정을 프로세스 인자로 덮어써 외부 통신 대상을 루프백 모의 서버로 고정한다. 운영의 환경변수나 기본값 파일은 수정하지 않는다. 결과는 별도의 로컬 실행 디렉터리에 JSON과 JVM 로그로 남고 이 문서는 검증한 결과만 요약한다. 외부 API 키나 운영 접속정보는 필요하지 않다.

실험용 스크립트는 로컬 보관 자료이므로 새 체크아웃에 자동으로 포함되지는 않는다. 같은 실험을 다시 수행할 때는 해당 로컬 스크립트를 보유해야 한다.

## 기능 테스트의 설정 주입

요청 제한 기능 테스트는 운영 환경변수나 운영 수치를 테스트 Java에 복사하지 않는다. `src/test/resources/rate-limit-test.yaml`에 경계 조건을 위한 합성 정책을 두고 `RateLimitTestSettings`가 읽어 각 생성자에 주입한다. 테스트 YAML에는 운영 변수 참조가 없으므로 로컬 운영 설정 변경이 기능 테스트의 승인 횟수를 바꾸지 않는다.

일반 실행 경로의 YAML 주입 성공과 필수 설정 누락 시 시작 실패도 별도 테스트한다. 테스트용 YAML의 값은 정책 예제나 운영 권장값이 아니다.
